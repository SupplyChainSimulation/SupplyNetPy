# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

SupplyNetPy is a Python library for discrete-event simulation of supply chains and inventory systems. It is a thin domain layer on top of [SimPy](https://simpy.readthedocs.io/): every node, link, replenishment policy, and demand generator is a SimPy process, and simulation time is advanced by `env.run()` (or the `simulate_sc_net` wrapper).

The public import surface is `SupplyNetPy.Components`, conventionally aliased as `scm`. `Components/__init__.py` re-exports an **explicit, curated** list of names from `core`, `logger`, and `utilities`, so users write `scm.Supplier`, `scm.SSReplenishment`, `scm.create_sc_net`, etc. Wildcard imports were removed in favor of `__all__` on every submodule — module-level imports (`simpy`, `random`, `copy`, `networkx`, `matplotlib.pyplot`, `logging`) and internal state (`global_logger`, `_rng`, `_LOGGER_KWARGS`, `_NODE_KWARGS`) are deliberately not reachable as `scm.*`.

## Architecture

### The two construction styles

Users can build a network in two interchangeable ways, and `create_sc_net` accepts either:

1. **Dict netlists** (the README / quick-start style): pass lists of plain `dict`s for `nodes`, `links`, `demands`. `create_sc_net` creates its own `simpy.Environment` and instantiates the right concrete class by looking at `node_type` (`supplier` / `infinite_supplier` → `Supplier`; `manufacturer` / `factory` → `Manufacturer`; `distributor` / `warehouse` / `retailer` / `store` / `shop` → `InventoryNode`).
2. **Direct instantiation**: construct a `simpy.Environment` yourself, build `Supplier` / `InventoryNode` / `Manufacturer` / `Link` / `Demand` objects directly, then either call `env.run(until=...)` or pass them to `create_sc_net(env=env, ...)` and `simulate_sc_net`.

Mixing the two *within the same list* is not supported and rejected up-front: each of `nodes` / `links` / `demands` must be all dicts or all pre-built domain objects. `create_sc_net` scans every element (not just `[0]`), so a dict at index 0 followed by a `Node` instance at index 1 — the exact pattern that used to bypass the env-required guard — now raises `ValueError("<list> mixes dicts and <Cls> instances")`. When any list contains pre-built objects, `env` must be passed explicitly *and* every object's own `env` must match it (a pre-built instance tied to a different `simpy.Environment` also raises).

## Conventions to preserve

- **Public API comes from `SupplyNetPy.Components`**, not from `SupplyNetPy` directly. Don't add exports to the top-level `__init__.py` without a reason. Every new public symbol must be added to three places: its module's `__all__`, the matching `from ... import` block in `Components/__init__.py`, and that file's top-level `__all__`. Internal plumbing (`global_logger`, `_rng`, the kwarg-whitelist sets) stays out.
- **Replenishment and supplier-selection policies are passed as classes**, not instances (`replenishment_policy=scm.SSReplenishment, policy_param={'s':100,'S':150}`). The owning node constructs them internally.
- **Lead times, arrival intervals, order quantities, disruption times** are passed as zero-arg callables (often `lambda: 2` or `lambda: random.expovariate(...)`) so they can be resampled per event. Scalars get auto-wrapped in `Node.__init__`, but APIs generally assume callables.
- Validation helpers `validate_positive`, `validate_non_negative`, `validate_number` live at the top of `core.py`; use them rather than hand-rolling checks so errors go through `global_logger`. `Link.__init__` and `Demand.__init__` additionally call `validate_number(name=..., value=callable())` after the scalar-auto-wrap, to catch callables that don't return numbers.
- `_info_keys` and `_stats_keys` drive `get_info()` / `get_statistics()` and are declared at **class level**, not in `__init__`. Add a new attribute by extending the class list declaratively: `class Supplier(Node): _info_keys = Node._info_keys + ["raw_material", "sell_price"]`. The `+` expression creates a fresh list per subclass, so siblings don't share mutation. Do **not** reintroduce `self._info_keys = [...]` or `self._info_keys.extend([...])` inside `__init__` — the §4.6 cleanup removed every one of those. Special case: `Statistics._stats_keys` and `Statistics._cost_components` are also class-level, but `Statistics.__init__` clones them onto the instance (`self._stats_keys = list(type(self)._stats_keys)`) because `Supplier` and `Manufacturer` append their own KPIs onto the instance — without the clone those appends would leak across every Statistics instance. New cost attributes still need to be appended to `self.stats._cost_components` so `Statistics.update_stats` picks them up — there is no substring-match fallback.
- **RNG control.** `core.py` owns a module-level `_rng = random.Random()` and exports `set_seed(seed)`. `Node.__init__` and `Link.__init__` accept an optional `rng: random.Random = None`; `None` falls back to `_rng`. Probabilistic disruption calls `self.rng.random()`, never the global `random.random()`. Seeding once (`scm.set_seed(42)`) before building the network is enough to make disruption deterministic. New probabilistic draws inside the library should resolve RNG the same way.
- **Kwarg filtering.** Node subclasses (`Supplier`, `InventoryNode`, `Manufacturer`, `Demand`) take `**kwargs` and forward them to both `Node` (via `super().__init__`) and `Inventory`. Two whitelist sets in `core.py` keep these clean: `_LOGGER_KWARGS` (`log_to_file`, `log_file`, `log_to_screen`) and `_NODE_KWARGS` (`failure_p`, `node_disrupt_time`, `node_recovery_time`, `logging`, `rng`, `logger_name`). Every call site that constructs `Inventory` must strip both sets out first — `Inventory.__init__` has a strict signature and will `TypeError` on unknowns (this is how typos like `shelf_live=` get caught instead of silently ignored).
- **`Inventory.level` and `Inventory.capacity` are read-only properties** that delegate to the underlying `simpy.Container` — the container is the single source of truth; don't shadow either attribute on the wrapper (§3.7).
- **`Inventory.put` returns the accepted amount.** The container's free-capacity clamp and the infinite/full/non-positive early-return paths make it possible for a `put(amount)` to accept less than `amount`. Callers that pre-increment `node.inventory.on_hand` before `yield`ing on `put` (`InventoryNode.process_order`, `Manufacturer.produce_product`) must reconcile by subtracting the shortfall (`requested - accepted`) from `on_hand`. Suppliers clamp upstream and don't need to reconcile.
- **Pending orders are counted, not flagged.** `InventoryNode` and `Manufacturer` expose `self.pending_orders: int` (starts at 0). `process_order` (resp. `process_order_raw`) increments it right after the capacity-clamp / early-return guards, at the real dispatch point, and decrements it on completion. Concurrent in-flight orders are intentional — a node may have more than one outstanding order if the replenishment policy keeps triggering. **Do not** reintroduce a boolean guard against re-entry.
- **Backorder-aware inventory position.** Everywhere replenishment quantity is computed or clamped, go through `node.position()`, which returns `on_hand - (stats.backorder[1] - inventory.waiting_site_orders())`. `on_hand` is inventory position (shelf + in-transit). A node's backorders hold two kinds of waiting orders: customers waiting for stock (not taken off `on_hand`, so `position()` subtracts them) and orders from other sites waiting in the shelf's SimPy queue (`Inventory.get` already took them off `on_hand`, so subtracting them again would count them twice — the §3.17 bug). The queue can also hold other requests made with `get`, so site orders are labelled: `InventoryNode.process_order` and `Manufacturer.process_order_raw` call `inventory.get(qty, site_order=True)`, `Inventory.get` passes `site_order` to every shelf request it creates, and `Inventory.waiting_site_orders()` sums only the labelled requests in `inventory.inventory.get_queue`. `Inventory.waiting_orders()` sums every waiting request. Any new code that places an order from another site must pass `site_order=True`, or `position()` will count that order twice. The capacity pre-check in both `process_order` methods uses `gross = self.position()`, so the clamp can't strand backordered orders behind a saturated shelf. `Manufacturer.manufacture_product` caps production at `on_hand - level + inventory.waiting_orders()` (units still to make — every waiting request was taken off `on_hand` but has not left the shelf, so this one uses the full total); dropping the `waiting_orders()` term makes a factory that owes more than its shelf holds stop producing for good. Do not compute `on_hand - stats.backorder[1]` by hand anywhere.
- **Backorders are live; shortage is a running total.** `stats.backorder` is what a node owes *right now*. A customer adds to it when they start waiting and removes it when served or when their patience runs out. An order from another site (`InventoryNode.process_order`, `Manufacturer.process_order_raw`) adds to it only if it really has to wait — checked with `not event.triggered` right after `inventory.get(...)`, only for an order that is really placed (`Node.place_order` checks that the supplier can take the order before `process_order` starts) — and removes it once `yield event` returns. `stats.shortage` records how short the node was when the demand arrived, and is never reduced, whether the order is later served or abandoned. A supplying site is counted as short only for an order it really receives: `process_order` records the shortage, and it runs only once `place_order` has found a supplier that can take the order. Do not record a shortage for an order that is not placed (the §3.20 bug: a site that was down was counted as short for every order it never received). A waiting customer's shortage is recorded once, when the order arrives (in `Demand._enqueue_for_tolerance`); `Demand.wait_for_order` must not record it again when a check finds too few units (the §3.22 bug: the same missing units were counted on every check).
- **`Statistics.reset()` starts the counting again; it does not change the present (§3.24).** It is what a warm-up uses (run, reset, run on). Running totals go to zero, but the values in `Statistics._live_keys` (`backorder`, `inventory_level`) are kept, the holding cost is brought up to date first (`inventory.update_carry_cost()`, skipped for an infinite inventory), and `inventory.instantaneous_levels` starts again. It must never touch the inventory itself (`on_hand`, the level, `pending_orders`, `raw_inventory_counts`, batches, waiting requests). A new statistic that describes the present goes in `_live_keys`. Both kinds of buying site record `demand_placed` and `transportation_cost` when the order is placed, before `inventory.get(...)`, not once the supplier serves it (§3.25).
- **Statistics that are worked out when read are properties, and `reset()` skips them (§6.9).** `Statistics` keeps running totals (counts, units, times) and works out averages from them when they are read: `elapsed_time`, `availability`, `disrupted_time`, `avg_waiting_time`, `inventory_level_time`, `zero_inventory_time`, `avg_inventory_level`, `zero_inventory_share`. They are `@property`s listed in `_stats_keys`, return `None` when there is nothing to divide by (or, for the inventory ones, for an infinite inventory or a customer demand), and must be skipped by both passes of `reset()` (setting a property raises an error). The clock is `start_time`, which `reset()` moves to `env.now`. `Inventory.update_carry_cost` adds up `level_time` and `zero_level_time` beside `carry_cost`; the properties add the stretch since the last update without changing anything stored. A disruption is recorded through `stats.disruption_started()` / `disruption_ended()` from `Node.disruption`. Where each new total is recorded: `blocked` in `Node.place_order`, the second check of `InventoryNode.process_order` and `Manufacturer.process_order` (each order once), and only when `node.has_suppliers()` is true, so it counts disruptions only. A site with no supplier at all (a manufacturer: no raw-material supplier for some raw material) is a setup mistake: `place_order` warns once per site and records nothing; `lost_sales` in the four `Demand` paths where customer units are never delivered (a no-tolerance customer loses the whole order, although `shortage` records only the missing units); `waited` / `waiting_time` at the site an order waits at, for customers and for orders from other sites; `dropped_qty` at the safety stop of `InventoryNode.process_order`. `simulate_sc_net` adds up only `lost_sales` and `disruption_lost_sales` for the network.
- **Each link records the replenishment orders sent over it (§6.8).** `Link.__init__` creates `link.stats`, a `LinkStatistics`. Every place that records a replenishment order at a site records it on the link too, right next to the node call: the second check of `InventoryNode.process_order` (`blocked`), placement (`shortage`, `demand_placed`, `transportation_cost`, `record_order(qty)`), `order_waits` (`backorder`, `waited`), and arrival (`fulfillment_received`, `inventory_spend_cost`, `waiting_time`, `lead_time`). Waiting time and lead time are added on arrival, not when the supplier serves the order, so their averages divide by `fulfillment_received[0]` recorded at the same moment, even across a reset. `Manufacturer.process_order_raw` does the same; its links never record `blocked`. `Link.disruption` calls `stats.disruption_started()` / `disruption_ended()`. Any new code that places a replenishment order must record it on its link as well, or the links stop adding up to the nodes (`TestLinkStatisticsAddUpToNodes`). Customers do not order over links. `LinkStatistics` follows the `Statistics` rules: values worked out when read are properties in `_stats_keys` and return `None` with nothing to divide by; `reset()` keeps `_live_keys` (`backorder`), moves `start_time` and counts an ongoing disruption from the reset. The two spreads of order sizes use Welford's method (no list of values); do not replace them with a stored list or a process that wakes every time unit. `link.get_statistics()` still returns only `status`. `reset_stats(supplychainnet)` / `Network.reset_stats()` reset every node, customer demand and link; the node and link tables share `_collect_stats` / `_format_performance` in `utilities.py`.
- **Factories make batch after batch, and every planned unit has its raw material ordered (§3.18).** `batch_size` is the factory's capacity: at most that many units per batch, each batch taking `manufacturing_time`. `Manufacturer.behavior` calls `manufacture_product()` (one batch; returns the units made) and goes straight on to the next batch whenever one made something. Only when nothing can be made (nothing planned, no raw material, or no free shelf space) does it wait on `production_wake`, fired by `Manufacturer.wake_production()` from three places: raw material arriving (`process_order_raw`), a new plan (`process_order`), and stock leaving the shelf (`Inventory.get`, via `getattr`, since only manufacturers have the method). A wake-up never produces by itself — the loop re-checks and goes back to waiting — so extra wake-ups are harmless. **Do not** go back to waiting for the next raw-material delivery after every batch (the §3.18 bug: raw material for the rest of a plan sat unused and the factory stopped for good). `Manufacturer.process_order` adds planned units to `on_hand` only after it has found, for every raw material, the first connected supplier whose link and site are both working; if any raw material has none, it plans and orders nothing. It then orders every raw material for those units, even while earlier raw orders are on their way — several at once are fine, as for distributors. **Do not** reintroduce the `ongoing_order_raw` flag, a "raw material already on hand is enough" check, or any other path that adds units to `on_hand` without ordering their raw material: such units can never be made, yet they keep the position above s, so the policy stops planning and orders waiting for them wait forever.
- **A limited supplier mines until its shelf is full and starts again as soon as stock is taken (§3.19).** `Supplier.behavior` waits on `inventory_drop` when its shelf is full. `Inventory.get` signals `inventory_drop` for *every* node that has the event (looked up with `getattr`), not only for nodes with a replenishment policy — suppliers never have one. **Do not** bring back the `if self.replenishment_policy:` condition around that signal (the §3.19 bug: a supplier whose shelf had once been full never mined again, and factories buying from it waited forever), and do not add separate "the supplier is short" signals in ordering code: the signal belongs where stock really leaves a shelf. Suppliers have no replenishment policy; an optional mining policy is a possible future feature, with today's behaviour as its default.
- **Disruption blocks new orders in `place_order`, not in-flight ones (§3.23).** `Link.can_take_order()` is the one rule: an order can go over a link only if neither the link nor its supplier's site (`link.source.node_status`) is disrupted. `Node.place_order` checks `self.can_place_order()` first and places nothing (one log line) if it is false; `InventoryNode` needs at least one supplier that can take the order, and `Manufacturer` overrides it so every raw material needs one. `InventoryNode.process_order` checks `supplier.can_take_order()` again when it starts, *before* shortage bookkeeping and before `pending_orders` is incremented, because that is when the order is really placed — `place_order` only queues the process. **Do not remove this second check:** processes queued before it run first, and at time 0 that includes the start of every disruption process, whose first random draw can disrupt the link or site `place_order` just chose (a link is always created after its buyer, so this is the normal case for `link_failure_p`). `Manufacturer.process_order` picks a supplier per raw material via `_raw_material_links()` when it starts and plans nothing if one is missing; `process_order_raw` has no checks (every disruption process has started by then). A blocked order creates no shortage, backorder or `pending_orders` entry. Customers follow the same rule (§3.26): `Demand.customer` checks `demand_node.node_status` first, and a customer who arrives while the site is disrupted is recorded only in the site's `stats.disruption_lost_sales` (not in `demand_received`, `shortage`, `backorder`, or the customer demand's `demand_placed`). Keep it apart from `shortage`: a shortage is units the site did not have, a disruption lost sale is an order it could not take. Customers already waiting when the disruption starts keep waiting and are still served. Ongoing shipments are intentionally not interrupted by a later disruption — that would require per-shipment process tracking on the `Link`, which is deferred.
- **A recovering supplier or link wakes its buyers (§3.23).** A policy without a review period is woken only by `inventory_drop`. When an order is blocked and the buyer has no units left, nothing leaves its inventory, so without help it would never order again. So `Node.disruption` calls `link.sink.wake_replenishment()` for every link in `self.buyers` when the node recovers, and `Link.disruption` calls `self.sink.wake_replenishment()` when the link recovers. `Node.wake_replenishment()` fires `inventory_drop` if it is not already fired; extra wake-ups are harmless (the policy re-checks its position and waits again), and periodic policies ignore it. Do not make `place_order` itself wait for a recovery: that would force every policy to `yield from` it, and the order would be sized from a position that is out of date by the time the supplier recovers.
- **Supplier-selection policies skip disrupted suppliers and links.** Two helpers on the base `SupplierSelectionPolicy` enforce this uniformly across `SelectFirst` / `SelectAvailable` / `SelectCheapest` / `SelectFastest`: `_active_suppliers()` returns the links with `can_take_order()` (both the link and the supplier's site active; it falls back to the full list if none, but `place_order` never calls `select` in that case), and `_apply_mode(selected)` centralises the fixed/dynamic behavior. In `"fixed"` mode, if the locked supplier or its link is disrupted, the policy temporarily returns a dynamically-chosen alternative *without* changing the lock — routing resumes through the locked supplier once it recovers. When adding a new selection policy, follow the same three-step pattern: `candidates = self._active_suppliers()`, apply the criterion to `candidates`, then `return self._apply_mode(selected)`.
- **Auto-wrap callables through `ensure_numeric_callable`, never inline.** Constructors that accept "scalar OR zero-arg callable returning a number" (`lead_time`, `node_disrupt_time`, `node_recovery_time`, `link_*_time`, `delivery_cost`, `order_arrival_model`, `order_quantity_model`, `manufacture_date`) must call `ensure_numeric_callable("name", value)` instead of the legacy `if not callable(x): x = lambda v=x: v` + optional `validate_number(value=x())` pair. The helper does the auto-wrap and a single validation invocation in one place, so passing a callable that returns a non-number (e.g. a class — `Foo` is callable but `Foo()` is a Foo, not a number) fails fast at construction with a clear error message naming the parameter. Stateful generators have their first sample consumed at construction; pure-function callables (the common case) are unaffected.
- **Stats vocabulary: `shortage`, not `orders_shortage`.** §6.6 renamed the node-level attribute to match the network-level `supplychainnet["shortage"]`. New code reads/writes `node.stats.shortage` and passes `update_stats(shortage=...)`. The `orders_shortage` name survives only as: (a) a property alias on `Statistics` for back-compat reads, and (b) a kwarg shim in `update_stats` that folds `orders_shortage=` onto `shortage=`. Do not introduce new uses of the old name.
- **Network wrapper is additive, not replacing.** `scm.Network` (in `utilities.py`) wraps the supply-chain dict with typed properties (`net.nodes`, `net.results`, `net.simulate(...)`). `Network.as_dict()` returns the same dict the legacy `create_sc_net`/`simulate_sc_net` write to — the two APIs share storage, so mutations via one are visible through the other. Do not duplicate state by copying the dict into the Network. New examples may use either style; legacy callers that read keys off the dict directly keep working.
- **`simulate_sc_net` logging knobs.** `logging: bool` controls whole-run logging; `log_window=(start, stop)` carves out a sub-interval. The original overloaded `logging=(start, stop)` spelling is still accepted but routed onto `log_window` with a `FutureWarning` (see the warnings bullet). Do not re-introduce the overloaded form in new APIs.
- **Setup problems use `warnings`; run-time events use `logging`.** Python's guidance: `warnings.warn()` when the user should change their code, `logging.warning()` when the event should just be recorded. Library logging is off by default, so a setup problem reported only to the log is never seen. A problem in how the model is set up or called (unused `policy_param` keys, a manufacturer missing a supplier for a raw material, a site with no supplier at all, a buyer that can order more than its supplier can hold (§3.27: warned once per pair when the link is created, by `Link._warn_if_buyer_can_order_more_than_supplier_holds`, with both site IDs in the text on purpose so every pair is listed, and again, briefly, when such an order is placed, by `Node._warn_if_supplier_cannot_hold`), an unknown name passed to `update_stats`, `simulate_sc_net` with a `sim_time` not past `env.now`, the deprecated `logging=(start, stop)`) calls `warnings.warn` **and** writes the same text to the log, so the trace stays complete. Keep the node's ID out of a warning's text when many nodes can trigger it, so Python shows it once, not once per node. Events during a run (partial puts at full capacity, dropped delivery units, an order larger than capacity) stay log-only: they recur and carry a time. Use `UserWarning`, or `FutureWarning` for deprecations (`DeprecationWarning` is hidden outside `__main__`). Tests that trigger a warning wrap the call in `pytest.warns`.
- **`Inventory.remove_expired` is event-driven, not polling.** The daemon sleeps until the head batch's `mfg_date + shelf_life` and wakes early via `self.perish_changed` (a SimPy event on `Inventory`). `Inventory.put` succeeds `perish_changed` only when the new tuple lands at index 0 of the heap — detected via `self.perish_queue[0] is new_batch` after `heappush`, which is true on empty→non-empty and on backdated batches that displace the head, and false on the common monotonic-restock case. The daemon rotates a fresh `self.perish_changed = self.env.event()` on each wake-up, mirroring the `wait_for_drop` rotation idiom. **Do not** reintroduce a `yield self.env.timeout(1)` poll, and do not signal `perish_changed` unconditionally on every put — both would re-create the §5.1 wake storm. The removal loop pops each expired batch and takes the same units off the shelf with `_InventoryContainer.remove_now` (see the perishable-batches bullet below), so expired goods never wait in line behind an order.
- **Perishable batches leave the list of batches at the moment their units leave the inventory (§3.21).** `Inventory.inventory` is an `_InventoryContainer` (a `simpy.Container` subclass), not a plain container. Its `_do_get` picks the batches (oldest first, via `Inventory._pick_oldest_batches`) at the same moment it takes the units out of the inventory, and stores them on the request (`_InventoryGet.batches`). `Inventory.get` returns that list, so it is filled in when an order is served, not when it is placed — callers read it after `yield event`. `_InventoryContainer.remove_now(amount)` removes units at once, ahead of any waiting requests; `remove_expired` and `destroy` use it. The invariant is that `perish_queue` always adds up to the inventory level. **Do not** pick batches inside `Inventory.get` before the request is served (the §3.21 bug: an order that had to wait got batches for only the units in the inventory when it was placed, the buyer lost the rest, the old units' expiry was missed and they were shipped already expired), and do not remove expired or destroyed units with an ordinary `get` request (it waits in line behind orders the inventory cannot fill yet).
- **Replenishment-policy contract on `Node`.** Replenishment policies speak to their owning node through four methods, not by reaching into its attributes: `node.position()` returns `on_hand - stats.backorder[1]` (the backorder-aware inventory position); `node.place_order(qty)` checks `can_place_order()` and then wraps `selection_policy.select(qty)` + `env.process(process_order(...))`; `node.wait_for_drop()` is a generator that yields on `inventory_drop` and rotates a fresh event in on wake-up (use `yield from node.wait_for_drop()`); and on the supplier side, `Link.available_quantity()` exposes `source.inventory.level` so selection policies compare candidates without reaching past the link. A new `InventoryReplenishment` subclass should call only these — a policy that directly writes `self.node.inventory_drop = ...` or spawns `process_order` itself is reintroducing the §4.3 coupling. Each built-in policy also declares `_param_keys`, the keys it reads from `params`; `InventoryReplenishment.__init__` warns (through `warnings.warn`, so it shows with logging off, plus a `global_logger` line naming the node) about any other key, asking whether another policy was meant. Keep the warning text free of the node's ID so Python shows each distinct warning once, not once per node. A new built-in policy must declare its `_param_keys`, including optional keys such as `period` or `first_review_delay`; `None` (the base default, used by custom policies) skips the check.
- **Link registration goes through `Node.add_supplier_link` and `Node.add_buyer_link`.** `Node.__init__` initialises `self.suppliers = []` and `self.buyers = []` for every node (so any Node subclass can be either end of a Link). `Link.__init__` registers itself with its sink by calling `self.sink.add_supplier_link(self)` and with its source by calling `self.source.add_buyer_link(self)`, instead of mutating the lists directly — the methods validate that the argument is a `Link` and that `link.sink is self` (resp. `link.source is self`). `buyers` is what a recovering node uses to wake its buyers (§3.23). Do not reintroduce `self.sink.suppliers.append(self)` or re-set `self.suppliers = []` inside subclasses: the former is the §4.4 coupling and the latter would clobber any Links already registered on `self.suppliers` via auto-registration.
- **Logging is opt-in and configured in one place.** `GlobalLogger` subclasses `logging.LoggerAdapter`; call levels directly on it (`global_logger.error(...)`, `node.logger.info(...)`) — do not reintroduce the `node.logger.logger.<level>(...)` double-hop the §4.9 cleanup removed. `GlobalLogger()` is inert at construction (NullHandler only — no file is opened). The trace file is opened the first time `enable_logging(log_to_file=True, ...)` is called, which `simulate_sc_net(logging=True)` does for the user. **Do not** reintroduce per-node `enable_logging()` calls inside `Node.__init__`: that was the §4.8 bug — every Node opened `simulation_trace.log` with `mode='w'` at construction, truncating the file N+1 times during network setup. Per-node loggers are children of `sim_trace` (`f"sim_trace.{node.ID}"`) so their records propagate to `global_logger`'s handlers without per-node FileHandler creation. `disable_logging()` is now scoped to the wrapper's own logger (sets `self.logger.disabled = True`) — do not re-introduce `logging.disable(logging.CRITICAL)`, which is a process-wide kill switch and would silence the host application's own loggers as a side effect.
- **Probabilistic disruption polls once per tick.** `Node.disruption()` and `Link.disruption()` both have the shape `if disrupt_time / else: <draw>; yield env.timeout(1)`. The `yield env.timeout(1)` is **outside** the `rng.random() < failure_p` check — it must fire whether or not the draw hit. Putting the yield inside the hit branch (the §3.16 bug) means a missed draw falls through `while True` with simulation time not advanced, busy-spinning in real wall time and drawing the rng unboundedly per tick until one finally lands under `failure_p`. The observable effect was that any positive `failure_p` collapsed to "near-certain disruption at t=0" instead of behaving as a per-tick probability. Do not move the yield back inside the conditional, and do not introduce a new probabilistic disruption path that omits the per-tick yield. The timed (`disrupt_time`) branch is unaffected — it has always yielded its own `timeout(disrupt_time())`.
- **Disruption inventory effects fire at the active→inactive edge, not throughout.** `Node.__init__` accepts `disruption_impact` (string preset, callable, or `None`) and resolves it once into `self._disruption_impact_fn`. The hook is invoked from `Node.disruption()` exactly once per disruption — at the moment `node_status` flips to `"inactive"` — on both the timed (`node_disrupt_time`) and probabilistic (`failure_p`) paths. Effects that should accrue *during* the outage (slow spoilage, ongoing theft, lead-time multipliers post-recovery) belong in a custom callback that spawns its own SimPy process and ties into `node_recovery_time`; do not reintroduce per-tick polling inside `disruption()`. Built-in presets `"destroy_all"` and `"destroy_fraction"` route through `Inventory.destroy(amount, reason)`, which removes the stock at once (through `_InventoryContainer.remove_now`, ahead of any waiting orders) and **must not** signal `inventory_drop` to a node with a replenishment policy — the dispatch gate already blocks new orders while the node is inactive, and triggering the wake event would queue replenishment orders that fire on recovery (§4.3 coupling). It does signal a `Supplier` (which has no policy; the signal only restarts mining) and calls `wake_production()` on a factory (§3.21). For a `Manufacturer`, `"destroy_all"` also wipes `raw_inventory_counts` because the spirit of the preset is "all physical stock at this site is gone." Destroyed quantity flows into `Statistics.destroyed_qty`; destroyed monetary value flows into `destroyed_value`, which is in `_cost_components` and therefore rolls into `node_cost` (and profit) automatically — new disruption-effect callbacks should follow the same `update_stats(destroyed_qty=..., destroyed_value=...)` pattern instead of inventing parallel KPIs.
- **`node_type` is validated through the `NodeType` str-enum.** `NodeType` in `core.py` is the single source of truth for which node types exist (10 members including the previously-missing `SHOP`). `Node.__init__` calls `NodeType(node_type).value` to validate and store the normalized lowercase string — existing comparisons (`node.node_type == "demand"`, `"supplier" in node.node_type`) keep working because `NodeType` subclasses `str`. Users can pass either a string (case-insensitive via `_missing_`) or the enum member (`scm.NodeType.SUPPLIER`). `create_sc_net` dispatches via `_NODE_DISPATCH` in `utilities.py` — a `NodeType`-keyed mapping to `(constructor_class, counter_key, drop_node_type_kwarg)`. Adding a new node type is a single-site change on `NodeType` plus an entry in `_NODE_DISPATCH`; do not reintroduce the hard-coded string ladders (`node_type.lower() in [...]`) that the §4.7 cleanup removed.
- **`Inventory.put` is hardened against the float-overshoot at the capacity wall.** A fill-to-capacity put (`amount = capacity - level`) routes through SimPy's `Container._do_put`, which does `_level += amount`; `level + (capacity - level)` can float-round one ULP *above* `capacity` (e.g. `99.99` → `99.99000000000001`). Two guards keep this from crashing: (1) the top-of-`put` early return tests `self.inventory.level >= self.capacity` (**not** `==` — exact equality missed the over-the-wall state), and (2) after the fill-to-capacity clamp, `if amount <= 0: return 0` backstops any non-positive clamp before it reaches `self.inventory.put` (SimPy's `ContainerPut` raises `amount(=...) must be > 0.` on `<= 0`). Do not revert the `>=` to `==` or drop the post-clamp guard. Regression: `tests/test_core.py::TestInventory::test_put_at_capacity_wall_does_not_crash` (capacity `99.99`, the documented overshoot pair). This made the `india_v2` "unreachable sentinel capacity" workaround unnecessary, though that workaround remains harmless.

- **User-facing docs target a non-programmer audience.** The hand-written prose in `docs/*.md` and `README.md` was rewritten in the May 2026 audit pass to be readable by readers without a Python background. New or edited prose should follow the same style: introduce technical terms (`(s, S)`, `ROP`, `multi-echelon`, `lead time`, `inventory position`) with a one-line plain-English gloss on first use; open lead paragraphs with a concrete narrative or scenario before the formal abstraction (the newsvendor page is the template — it now starts "Imagine a newspaper vendor who buys copies wholesale every morning…" rather than "a decision-maker must determine the optimal order quantity"); avoid Python-internal jargon like *"generator function"* when the API just wants a zero-arg callable; and accurately describe SupplyNetPy as **event-driven** (it jumps from one event to the next via SimPy), never *"time-stepped"* or *"steps through time"* — the latter is technically false and was caught in review. The detailed `disruption_impact` discussion lives in `docs/api-reference/api-intro.md`; `docs/ten_min.md` is the quickstart and intentionally does *not* mention it. Five orphan tooltip definitions (`[qt]`, `[ss]`, `[sssafety]`, `[rq]`, `[periodic]`) used to sit at the top of `ten_min.md` with no body references — they were removed; do not paste them back in.
- **Code comments and docstrings are written in plain, simple language too.** The plain-language rule above is not limited to `docs/*.md` and `README` — it applies to *in-code* comments, docstrings, and any explanatory text. SupplyNetPy is a public library, so people who use or extend it must be able to follow the code easily. Avoid internal jargon and shorthand (e.g. *"delta cycle"*, *"drain"*, *"on_hand pre-increment"*, *"zero-time spin"*, *"(s,S) position math"*); when a technical term is genuinely needed, gloss it in plain words on first use. Explain *why*, not just *what*, and use a concrete picture where it helps. The looped-`put` comments in `InventoryNode.process_order` (core.py ~2917) are the template: they describe an over-capacity replenishment as "an order bigger than the free space on the shelf," explain `env.timeout(0)` as "pause one instant of simulation time — it does not advance the clock, it just lets other events for this same instant run," and gloss `on_hand` as "the node's inventory position: units on the shelf plus units still in transit." Keep Google-style docstring sections (`Parameters` / `Attributes` / `Returns`) intact for `mkdocstrings`, but phrase their prose plainly.
- **One word per idea: use the glossary (`docs/glossary.md`).** Comments, docstrings and docs use only the terms defined in the glossary, so that technical readers never meet two words for the same thing. Plain language still applies, but it *explains* a glossary term in plain words on first use ("inventory level (the units physically at the site)") instead of swapping in a friendlier synonym. New names (classes, methods, variables) follow the same terms. When a new idea needs a word, add it to the glossary first. Released public names that use another word stay as they are, for compatibility (`inventory.on_hand` is the inventory position before customer backorders; `site_order`, `waiting_site_orders()`, `demand_by_site` refer to replenishment orders; `extraction_quantity` / `extraction_time` refer to mining; `inventory_carry_cost` is the holding cost; the parameter `supplier` of `process_order` / `process_order_raw` is the **Link** to the supplier, so say so wherever it is documented). Key distinctions: a **node** is any point including customer demands, a **site** is a node that holds inventory (every node except a `Demand`); the **supplier** of a site is the site at the other end of a link (`link.source`), while a **raw-material supplier** is the `Supplier` class; a **buyer** is a site that buys from another site (`link.sink`), a **customer** is the end customer; a **batch** is units with the same manufacturing date, a **production batch** is what a manufacturer makes in one go (`batch_size`). Words to avoid, with the glossary term to use instead: shelf / stock / stock on hand / units on the shelf → inventory level (keep "shelf life" and "safety stock", which are standard terms); "on hand" in prose → inventory position; facility / location / actor → node or site; route / lane / edge → link; upstream node / vendor → supplier; downstream node → buyer; consumer / end user → customer (and never "buyer" for a customer); demand point → customer demand; endless supplier → infinite supplier; factory / plant / production unit → manufacturer; items / goods / products (for quantities) → units; item → product; component / material → raw material; made-on date / mfg date → manufacturing date; lot / dated batch → batch; batch (alone, for production) / run → production batch; spoiled / perished → expired; request → order ("request" only for the SimPy object waiting at an inventory); site order (in prose) / reorder (noun) → replenishment order; shipped / delivered (as the statistic) → fulfilled; transit time / delivery time → lead time; backlog / pending order → backorder; stockout / unmet demand → shortage (units missing when the order arrived), lost demand → lost sales (customer units never delivered), and customers turned away by a disruption → disruption lost sales; split delivery → partial delivery; reorder rule / inventory policy / ordering policy → replenishment policy; min-max (in prose) → (s, S) policy; extraction (in prose) → mining; carrying cost / carry cost (in prose) → holding cost; purchase price / sale price → buy price / sell price; shipping cost → transportation cost; total cost (for one node) → node cost; outage / failure / down / broken down → disruption; failure probability (in prose) → disruption probability; repair → recovery; tick / time step / day (as the unit) → time unit; time-stepped → event-driven; graph (except the drawing) → supply chain network; in the pipeline → in transit.
